# Technical overview

npuforge demonstrates checkpoint-to-QNN conversion inside an Android app.
A user supplies an SD1.5 or SDXL checkpoint and optional UNet LoRAs. Native tools
populate pre-authored graphs with those weights and invoke Qualcomm's ARM64
context generator on the phone. Output models work only with
[Local Dream](https://github.com/xororz/local-dream) and
[Fancy-Ai](https://github.com/Mr-J-369/Fancy-Ai).

## The engineering contribution

Most of the expensive graph export and calibration is performed once per
supported template. Subsequent conversions reuse graph structure and activation
encodings while regenerating the checkpoint-dependent weights and scales.
A compact recipe specifies each tensor's source, layout and quantization rule.

For the original SD1.5 template, an 863 MB weight pack was reduced to a **43,328
byte** constants pack plus a roughly **397 KB** recipe. The surviving constant
payload is 832 bytes across 257 entries. Learned weights are supplied by the
selected checkpoint. These sizes exclude model libraries, runtime libraries and
other assets; they are not an APK size claim.
[Derivation and byte comparisons](PIPELINE.md).

## Preparation and phone execution

| Phase | Workstation, once per template | Phone, for each checkpoint |
|---|---|---|
| Graph definition | Export graph and choose tensor interfaces | Load bundled graph library |
| Quantization | Calibrate fixed activation ranges | Recompute checkpoint-dependent weight encodings |
| Weight mapping | Author layout/quantization recipes | Stream checkpoint tensors through those recipes |
| LoRA | No per-adapter host preparation required for supported formats | Merge supported UNet tensors before quantization |
| Compilation | Build the ARM64 pack-loading model library | Run QAIRT `qnn-context-binary-generator` |
| Export | Bundle required developer assets in APK | Write component files and importable ZIP |

A new architecture, graph shape or calibration strategy still requires template
authoring. This implementation does not perform fresh activation calibration
for each checkpoint on the phone.

## Components and formats

| Component | SD1.5 | SDXL | Export/runtime |
|---|---|---|---|
| UNet | 512 × 512 template | 1024 × 1024 template | QNN context; W8A16 |
| Text encoders | CLIP-L, clip-skip 2 contract | CLIP-L and CLIP-G | MNN graphs and embeddings |
| VAE encoder | Checkpoint weights | Checkpoint weights | QNN context; FP16 internal arithmetic |
| VAE decoder | Checkpoint weights | Checkpoint weights | QNN context; FP16 internal arithmetic |
| Tokenizer | Bundled standard tokenizer | Bundled standard tokenizer | JSON |

CLIP-L uses FP16 weights; SDXL CLIP-G uses the established MNN INT8 format.
CLIP output semantics and the consumer's conditioning layout must agree.
SDXL exports carry the `231_masked_v1` interface marker. Fixed QNN targets are
currently v73/soc43 for SD1.5 and v75/soc57 for SDXL; the app does not dynamically
select a graph target for each device.

See [SD1.5 components](SD15-COMPONENTS.md), [SDXL components](SDXL-COMPONENTS.md)
and [SDXL graph contract](SDXL.md).

## Memory and process design

The weight converter computes scales first and streams tensor payloads in a
second pass. LoRA merged-weight caching is bounded to 128 MiB, with evicted
weights recomputed using the same arithmetic.

The SDXL compiler runs with a dedicated C/C++ allocator that stores allocations
in file-backed mappings. Small objects and allocations up to 1 MiB share 8 MiB
slabs; larger allocations use separate backing files. Pooling reduces the
number of virtual memory mappings generated by many small compiler objects.
Backing storage is not equivalent to resident RAM, and available disk capacity
remains part of the conversion budget.

Each VAE component and the UNet compile in separate subprocesses, allowing
process memory to be released between graphs. Active inputs and backing files
live under `noBackupFilesDir`, outside reclaimable app cache. The service removes
temporary data after completion or cancellation.

The measured failure modes and latest fixes are recorded in the
[device investigation](SDXL-INVESTIGATION.md). They describe specific observed
SDK/device behavior, not a general conclusion about all Snapdragon devices.

## Android integration

- Executables are packaged as `lib*.so` under `nativeLibraryDir`, with legacy
  native-library extraction enabled.
- Qualcomm libraries are preserved during packaging; DSP skeletons are made
  available from a location accessible to FastRPC.
- A foreground service runs conversion and exports diagnostics. Final ZIPs are
  written through MediaStore into `Download/npuforge/`.
- New checkpoint conversion uses local files and bundled assets. Legacy component
  backup/download functionality is separate from that conversion path.

[Android packaging details](ANDROID.md).

## Evidence and evaluation

Native weight packs are compared against the Python/reference conversion bytes.
The compiler's context binary hash is not an equivalence criterion: builds can
produce different binary hashes while producing identical rendered output.
Host regression tests cover tensor transformations, floating-point conversion,
LoRA merging, sparse component recipes and allocation behavior.

Phone results include the original SD1.5 pack equivalence and rendered-image
comparisons, SDXL conversion on Galaxy S25 Ultra, and reported successful Pony,
Illustrious and LoRA cases. Timing scope, missing measurements and reproducible
evaluation steps are in [Results](RESULTS.md).
